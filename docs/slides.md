## 第 1 頁　一句話說清楚：我做了什麼
**標題**：幫法務「先看出可能的個資法疑慮」，每項都附法條原文，最後由人決定
- 圖：流程縮圖（上傳 PDF → 系統標出疑慮 → 法務確認／駁回）
- 三個數字：個資法 **66 條**真實入庫｜**3 種**審閱畫面｜**4 份**展示合約

【開場 30 秒：先講定位：系統只提示可能疑慮，不判定違法。接著馬上 demo。】

## 第 2 頁　先問清楚，再動手
**標題**：開工前先確認 3 件事，因為它們決定架構
| 問題 | 答案 | 影響 |
|---|---|---|
| 給誰用？ | 法務人員 | 每項疑慮都要附原文作為依據 |
| 合約格式？ | PDF（含掃描檔） | 需要 OCR |
| 外規是什麼？ | 法條庫 → 先做個資法 | 66 條，2 小時做得完 |

- 沒有 AI key → 改用本機模型，**資料也不會離開本機**

【這頁對應考題的「可以向面試官釐清需求」。】

## 第 3 頁　架構與取捨
**標題**：2 小時內把整條流程打通，只做 1 部法規；做不完的部分標成示意
- 圖：架構圖（藍色實線＝已實作，灰色虛線＝示意）
- 做了：OCR、規則＋本機 AI、引用驗證、人員複核
- 先不做：多部法規、向量檢索、帳號權限，各自附原因

【強調取捨的理由，不只是列清單。】

## 第 4 頁　法條從哪來、存成什麼樣子
**標題**：法條是真的抓下來的，可以追溯到原始網頁
- 來源：法務部全國法規資料庫（個資法 pcode I0050021），原始 HTML 有保存
- 驗證：三種方法數出來的條數一致（66 條），並抽查 3 條原文
- 圖：7 張資料表的關係（法規 → 法條｜合約 → 條款 → 疑慮 → 複核紀錄）

【複核紀錄只新增、不覆蓋 → 每次決定都能追溯，這是稽核需求。】

## 第 5 頁　畫面：替法務設計的三種審閱方式（新）
**標題**：同一套後端，三種畫面對應三種工作情境
| 版本 | 適用情境 |
|---|---|
| A 分割檢視 | 短合約，一眼看完全部條款和疑慮 |
| B 審閱佇列 | 大量複核：用鍵盤 J/K/Y/N、看進度條、匯出 CSV |
| C 全文標註 | 從頭讀合約，有疑慮的條款直接上色 |
- 共同設計：法條原文放在疑慮旁、標示來源是規則還是 AI、免責聲明常駐、駁回時可以留理由
- 圖：三版畫面截圖並排

【誠實說明：這三版還沒給真正的法務試用過，下一步要做易用性測試。】

## 第 6 頁　怎麼驗證：測試 ≠ 準確（核心頁）
**標題**：測試通過只代表功能正常；準確度要用盲測來看
- 圖：長條圖（v1 規則 2/9 → 規則＋AI 4/9 → v2 規則 9/9 ⚠ 過度擬合 → **盲測 0/3**）
- 自動化：17 個驗收測試，加上 Playwright 端對端測試（三種畫面都涵蓋）
- 展示合約：明顯違規 5/5｜合規範本 0 誤報｜換句話說的寫法 0/6

【這是全場最重要的一頁：我刻意留一份盲測合約，才沒有被 9/9 騙到。】

## 備用 A　我怎麼檢查 AI 的產出（被問到時再翻出來）
**標題**：AI 說完成了，不代表真的完成
- 例子：OCR 認錯字 → 放寬比對；伺服器跑舊版 → 重啟重測；練習題全對 → 加新考卷（盲測）
- 三層把關：只能引用候選法條 → 程式驗證條號存在 → 人員複核
- 圖：timeline.md 裡「檢查 AI 產出的關鍵時刻」表
