# 從面試官角度：這題想看到什麼

## 考題字面背後的 6 個觀察點
| 考題字句 | 面試官想看的 | 你的對應證據 |
|---|---|---|
| 「可以向面試官釐清需求」 | 會不會先問再做。直接開始寫程式的人會扣分 | 開場先問了 3 個問題（給誰用、什麼格式、外規範圍） |
| 「請自行決定兩小時內要實作哪些部分」 | **取捨能力**，比做了多少更重要 | 第 2 頁的「做了／先不做／原因」表 |
| 「實際從公開來源取得法條，說明來源與取得方式」 | 資料是真的、可以追溯，而不是叫 AI 背出法條 | 保存原始 HTML，三種方式數出的條數一致 |
| 「請準備說明你如何檢查 AI 產出的結果」 | **這是重點題**：會不會盲目相信 AI | 引用驗證、答案卷、獨立實測、駁回機制 |
| 「區分已完成、尚未完成、仍需驗證」 | 是否誠實。過度包裝會被追問到破功 | 第 5 頁的三欄表；主動說出樣本偏樂觀 |
| 「不是對違法與否的最終判定」 | 對法律責任和產品定位有沒有感覺 | 系統定位是「提示可能疑慮＋人員複核」 |

## 很可能被追問的問題（先準備好答案）
1. **「AI 引用了錯的法條怎麼辦？」** → 有三層把關：AI 只能從候選法條中選、程式驗證條號存在於資料庫、最後由人員複核。要誠實說：實測中真正的問題是「條號存在但引錯」（例如引用了第 20-1、42、52 條），程式擋不住，只能靠第三層的人員複核。這也是系統定位成「提示」而不是「判定」的原因。
2. **「為什麼不用 ChatGPT 或 Claude？」** → 這次沒有 API key。另外合約通常是機密，用本機模型資料不會外流。介面已經抽象化，要換成雲端模型只需要改一個函式。
3. **「規則寫死，換一份合約就失效吧？」** → 對，而且我有實測數據證明：v2 規則在用來調整的 3 份合約上找到 9/9，換成盲測合約就是 0/3。本機 8B 模型在盲測合約上也是 0/3。結論是：要把準確度做起來，需要真實資料、能力更強的模型和語意檢索，這些都在下一步裡。
4. **「OCR 錯字會怎樣？」** → 實測中「洩」被辨識成「浅」，部分字變成簡體。目前是把規則放寬來應付，正式版會在 OCR 後加上繁簡轉換與錯字校正。
5. **「法規修正了怎麼辦？」** → `laws` 表有記錄修正日期和抓取時間。下一步是定期比對修正日期，有變更就重新匯入，並把之前的檢查結果標記為「依舊版法規」。
6. **「你怎麼確認 AI 寫的程式是對的？」** → 先寫規格與驗收測試，程式必須通過測試。另外用一份沒拿來調整的新考卷（盲測）做獨立實測，避免球員兼裁判。**原則：AI 說的每一個結論，都要回頭去看檔案、看程式碼、看實際輸出，確認之後才採用。**

7. **「換成雲端 AI，成本多少？」** → 費用和送進模型的字數成正比。目前每個條款會附上最多 6 條候選法條，所以費用大致是「條款數 × 候選法條字數」。一份 20 條的合約大約是數萬 tokens 的量級，實際金額要以模型的官方定價為準。降低成本的方法：只把規則沒命中、但檢索分數高的條款送給 AI；法條部分用 prompt cache 快取。**現場不要報出精確金額**，講算法就好。
8. **「要支援 10 部法規、上千份合約，架構要改哪裡？」** → ① 法規匯入程式改成可以指定法規代碼（pcode），資料表本來就有 `law_id`，不用改；② 檢索改成「關鍵字＋向量」混合；③ SQLite 換成 PostgreSQL＋pgvector；④ OCR 和 AI 改用工作佇列在背景處理，上傳後再通知結果。
9. **「上傳的合約存在哪？這工具本身也在處理個資吧？」** → 誠實回答：目前存在本機 SQLite，沒有加密，也沒有刪除機制，所以只能拿來展示。正式版需要：保存期限到了自動刪除、資料庫加密、存取權限控管加上稽核紀錄、上傳前提醒先去識別化；如果用雲端 AI，要確認服務商不會拿資料訓練模型，資料存放地點也要符合規定。這正好是個資法第 27 條「安全維護」的要求，我們自己也要做到。

## 容易扣分的地方（要避免）
- 把 17 個測試全過講成「準確率 100%」。測試只證明功能可以運作，不能證明檢查準確。
- 只展示成功的案例。要主動展示 AI 誤報、並由人駁回的那一段。
- 花太多時間講技術名詞。對方可能是法務或產品主管，請用流程圖說明。
